# 리스크 분류 기준 (Risk Rubric)

본 문서는 isms-p-audit Skill 이 발견 항목(finding)에 등급을 부여할 때 사용하는 기준이다.
모든 등급은 **두 축**의 곱으로 결정한다:

1. **위반 심각도 (Severity)** — 인증 심사 통과 영향 + 개인정보/시스템 영향
2. **증거 강도 (Confidence)** — 코드만으로 100% 확실 / 정황상 의심

---

## 5단계 등급 정의

### Critical (즉시 수정)

- **정의**: 인증 심사 시 결함(미흡 통제) 확정 가능성이 매우 높고, 동시에 법적 위반 또는 개인정보 유출 위험이 즉각적인 항목.
- **예시**:
  - 평문으로 저장되는 주민등록번호/계좌번호/비밀번호
  - 공개 인터넷에 노출된 데이터베이스 (RDS publicly_accessible = true)
  - 코드 또는 git 히스토리에 하드코딩된 운영 자격증명
  - 모든 사용자에게 부여된 AdministratorAccess
- **대응 SLA**: 48시간 이내 패치 + 자격증명 회전.

### High (심사 전 반드시 보완)

- **정의**: 미흡 통제로 분류될 가능성이 높지만, 즉각적인 유출 위험은 낮은 항목.
- **예시**:
  - MFA 강제 정책 미적용 (IAM 사용자, 관리자 콘솔)
  - 감사로그 보관기간 1년 미만 (개인정보처리시스템은 1년 필수)
  - TLS 1.0/1.1 허용
  - WAF/Rate Limit 부재로 무차별 공격에 취약한 인증 엔드포인트
  - DB backup_retention_period < 7
- **대응 SLA**: 심사 시작 2주 전까지 보완.

### Medium (보완 권장)

- **정의**: 심사관 재량 영역. 명시적 결함은 아니지만 보완하지 않으면 권고사항으로 지적될 가능성.
- **예시**:
  - 일부 API 에 audit log 누락 (전체는 있음)
  - SSH 접근이 VPN 내부지만 IP 제한이 추가로 없음
  - 비밀번호 정책이 8자 (권장 10자 이상)
  - 동의 철회 UI 가 있으나 처리 로그 미저장
- **대응 SLA**: 심사 시작 1개월 전까지 검토.

### Low (모범사례)

- **정의**: 심사 통과는 무난하나 보안 모범사례 측면에서 개선 권장.
- **예시**:
  - TLS 1.3 미사용 (1.2 사용 중)
  - Dependency 업데이트 주기가 분기 단위
  - HSTS preload 미등록
- **대응 SLA**: 다음 분기.

### Info (정보 제공)

- **정의**: 문제는 아니지만 사용자가 알아야 하는 정보. 주로 외부 증적이 필요한 항목 안내.
- **출처 제약**: Info 등급은 **Skill 단독에서만 발생** (manual_review 시그널 / glob_exists 부재 등 자동 판정 불가 영역). 외부 CLI 는 4단계 (critical/high/medium/low) 만 emit 하므로 CLI 단독으로는 Info 가 나올 수 없다.
- **예시**:
  - 정보보호 정책 문서 위치 확인 필요
  - 위탁사 점검 결과 보고서 준비 필요
  - 직원 보안교육 이수 기록 필요
- **대응**: 정보보호책임자에게 확인 요청.

## 등급 결정 매트릭스

| 증거 강도 ↓ / 심각도 →    | 인증 결함 + 즉시 위험 | 인증 결함 가능성 높음 | 권고 사항 가능성 | 모범사례 미적용 |
|---------------------------|----------------------|----------------------|------------------|------------------|
| 코드/IaC 명백 (high)      | Critical             | High                 | Medium           | Low              |
| 정황 강함 (medium)        | High                 | High                 | Medium           | Low              |
| 정황 약함 (low)           | High                 | Medium               | Medium           | Low              |
| 외부 증적 필요 (unknown)  | Info                 | Info                 | Info             | Info             |

---

## 등급별 보고서 표기 규칙

- Critical/High: 보고서 상단 요약에 별도 강조 박스. 권장 조치는 **언제까지** 누가.
- Medium: 본문에 정상 나열.
- Low: 별도 섹션 "개선 제안" 으로 묶음.
- Info: "외부 증적 필요" 체크리스트로 분리.

## 표현 가이드

자동화된 도구가 단정적인 표현을 쓰면 사용자가 잘못 인용할 수 있다. 다음 표현을 따른다:

- "위반입니다" (X) → "위반 가능성이 있습니다" (O)
- "결함입니다" (X) → "심사 시 결함으로 분류될 가능성이 높습니다" (O)
- "안전합니다" (X) → "코드 수준에서는 통제가 적용된 것으로 확인됩니다" (O)
- "통과" (X, 단정) → "코드 증적 OK" (O, 자동화 한계 표시)

## 출처 라벨 표기 가이드 (v0.3.1)

각 finding 에는 평가 출처 라벨을 붙여 신뢰도를 명시한다 (보고서 템플릿 §2 참조):

- `[검증된 OSS: prowler/<check_id>]` — 가장 높은 신뢰도 (Tier 2 권장 기본값)
- `[검증된 OSS: scoutsuite/...]` / `[검증된 OSS: kube-bench/...]` — 동등 신뢰도
- `[LLM aws CLI 직접 호출]` — fallback. 정확도 변동 가능. 보고서에 명시 필수
- `[Skill grep_absent]` / `[Skill grep_pattern]` — Skill 내장 정적 시그널
- `[CLI <ruleId>]` — 외부 CLI emit (예: `[CLI IAM-001]`)
- `[LLM 코드 분석]` — 시그널 없는 LLM 추론 (가장 낮은 신뢰도, 해석 주의)
